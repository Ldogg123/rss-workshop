# Changelog

## v1.3.0 — 2026-11-07

Existing RSS and Atom feeds as sources, cleanup rules that take share bars and other clutter out of descriptions and articles, an Accept-Language you can set for one feed, and a Quiet badge that now means no new story, after a time each feed can choose. Full-article feeds whose source answers 304 finish fetching their articles, and Chromium feeds that fall due together no longer fail. The database moves to schema 6, so going back to v1.2.0 means restoring a backup.

### Upgrading from v1.2.0

- **Update your checkout first** (`git pull`). The v1.2.0 `scripts/backup.py` refuses schema 6, so only the current one can back up an upgraded database; either one restores the schema 5 copy described below. There is no new setting, and the Compose files are unchanged. From v1.1.1 or older, also follow [Upgrading from v1.1.1](#upgrading-from-v111) and the notes of each release in between, which say which feeds change once.
- **The database moves to schema 6**, in one transaction, the first time this version starts. Databases from v1.1.0, v1.1.1 and v1.2.0 are at schema 5; older ones take every step in the same transaction. Each feed gains the time it last saved a new story, which [Quiet](docs/operations.md#quiet-feeds) now measures from, starting at the time it first saw the most recently added of its saved stories. The upgrade changes no published byte, GUID, publication date, `Last-Modified` or ETag, so readers keep receiving 304. Schema 6 also keeps older releases, which would ignore settings such as cleanup rules, from opening the database.
- **SQLite takes a copy for you.** Before upgrading, the app saves a verified copy to `backups/pre-upgrade-schema-5-<time>` in the data directory and names it in the log. It needs free space about the size of the database, which stored article bodies can make large; without that space, startup stops before changing anything. The copy sits on the same disk and is never deleted automatically, so keep an off-host backup too, and remove the copy once this version has been working. `UPGRADE_BACKUP=false` skips it. See [automatic copy](docs/operations.md#automatic-copy-before-an-sqlite-upgrade).
- **PostgreSQL gets no automatic copy.** Take a `pg_dump` before upgrading; the app logs a warning when it migrates. See [PostgreSQL backups](docs/postgresql.md#backup-and-restore).
- **Rolling back is a restore, not an image swap.** v1.2.0 and v1.1.x refuse a schema 6 database, so re-pinning the older image, as v1.2.0's notes describe, no longer works on its own. To go back, stop the app and restore the `pre-upgrade-schema-5-*` copy or a backup taken before upgrading into new storage with `sudo python3 scripts/backup.py restore` (see [restore into a new host directory](docs/operations.md#restore-into-a-new-host-directory)), or `pg_restore` the dump into a new database. Point `RSS_DATA_DIR` or `DATABASE_URL` at it, set `RSS_IMAGE` to `ghcr.io/ldogg123/rss-workshop:v1.2.0-browser`, `ghcr.io/ldogg123/rss-workshop:v1.2.0-static` with `compose.static.yaml`, or the image digest you saved, and start the app. Changes made since the upgrade are lost: new feeds, edits, reset reader links, and stories, which are fetched again while their sources still list them. To keep feeds added since, export their recipes first and import them afterwards, without the new settings below; imported feeds get new reader links. If the migration itself failed, nothing changed, and v1.2.0 opens the database as it is.
- **Quiet now means "no new story".** v1.2.0 marked a feed **Quiet** when its published output had not changed for 14 days, or 10 refresh intervals if that is longer. Now it is marked when no refresh has saved a new story for that long: one the feed did not have saved and that `MAX_ITEMS` retention kept. Changed descriptions, images and article bodies no longer count, nor do stories retention removes. So:
  - Feeds whose descriptions change at every refresh, for example with a relative age or a comment count, could never turn Quiet before and may turn Quiet right after upgrading.
  - Editing a feed's title, address or refresh interval no longer restarts the count once the feed has saved a story; for a feed that has never saved one, it still does.
  - `rss_workshop_feeds_quiet`, the **Quiet** status filter and the card follow the new rule, so review alerts built on the metric. The per-feed alert example in [metrics](docs/operations.md#metrics) now uses the new `rss_workshop_feed_last_new_story_timestamp_seconds` with a threshold of its own, so unlike `rss_workshop_feeds_quiet` it ignores **Mark as Quiet after**. `rss_workshop_feed_last_changed_timestamp_seconds` keeps its meaning, so alerts built on it work as before.
  - For a site that publishes rarely, set the new **Mark as Quiet after** in its editor to a longer time or to **Never**, and leave such a feed out of a per-feed alert by its `id` label.
- **Full-article feeds send more full requests while articles are missing.** So that a source answering `304 Not Modified` no longer stops a full-content feed at the articles it has (see Fixes below), such a feed in Static HTTP or Auto requests its list page without `ETag` and `Last-Modified` once after each start, and again after each refresh that leaves stories without an article while adding more; conditional requests resume once the backlog drains or stops growing. Sources see these extra full requests, after every restart too. Chromium and FlareSolverr never sent validators and are unchanged. A feed changes only as articles are stored, except where its page lists more stories without a date than `MAX_ITEMS` keeps: each full request saves again, under a new first-seen time, the ones retention removed, as every refresh of a source without validators already does. See [full article content](docs/atom.md#full-article-content).
- **Chromium refreshes wait for a free slot.** A refresh in Chromium mode, or one that renders its article pages in Chromium, in any mode but FlareSolverr, now starts only while one of the `BROWSER_SLOTS` is free. The rest stay due, without an error, a backoff or a notification, and start oldest first. A feed that renders its article pages now renders them one at a time instead of four, so a large backlog may take another refresh to fill in, and its preview fetches its three sample articles one at a time. An Auto feed that renders its article pages waits for a slot before its static list fetch too; other Auto feeds start as before, and their fallback render still waits for a slot inside the feed's deadline. **Preview items** and **Choose elements visually** are never refused, but may wait for a slot. A render that waits out its deadline for a slot now says so: its error starts with `no free Chromium slot before the deadline` instead of being a bare `context deadline exceeded`. Nothing published changes. See [Chromium capacity](docs/browser.md#capacity).
- **Recipe files that use the new settings need this version.** v1.2.0 and older refuse a recipe file in which any feed sets `accept_language`, `remove` or `quiet_days` (`json: unknown field "remove"`, for example) or is a feed source (`selector type must be css or xpath`), and import none of its feeds. To import such a file there, remove those fields and leave feed sources out. Recipes that use none of them export byte for byte as before. See [recipe export and import](docs/recipe-portability.md).

### New

- Read an existing RSS or Atom feed as a source. Choose **Source → RSS or Atom feed** in the editor to read an RSS 0.9x or 2.0, RSS 1.0 (RDF) or Atom feed instead of selecting a page's cards, then filter its stories, use library filters, clean out clutter, fetch full articles and publish it behind its own private RSS and Atom links. The feed supplies each story's title, link, description, image and date, so a feed source has no selectors; it is fetched as Static HTTP, and its article selector and cleanup rules are CSS. Stories are identified by their `guid`, Atom `id` or `rdf:about`, then their link, then their title. Untitled posts, as Mastodon publishes them, take the start of their text as a title, a post that is only a video embed publishes the entry's summary, and images an entry declares come before any image in its text, skipping images that declare a 0- or 1-pixel size, as tracking images do. The first 1,000 entries of a feed of up to 4 MiB are read; one malformed entry fails that refresh, and saved stories are kept. A saved feed cannot be switched between a web page and a feed source, because the two identify stories differently: **Duplicate** it and choose the other source in the copy. The demo site now ships its own `feed.xml`, read by the new `demo-feed-recipe.json`. JSON Feed, feed autodiscovery and OPML subscription import are not supported. See [feed sources](docs/feed-sources.md).
- Remove clutter from descriptions and articles. A feed can list selectors, one per line in the editor's new **Content cleanup** section, for parts to leave out of each description and article body, such as share bars, newsletter boxes or "Related" lists that the sanitizer keeps. Rules use the feed's selector type, CSS for a feed source, and match only inside the selected block, which is never removed; XPath rules start with `./`. A feed has at most 20 rules, each on one line of at most 1,000 characters. They run before sanitizing, skip a description or article read from an attribute, and do not change a web page's story image. Story filters match the cleaned description, while removing nonmatching saved stories judges the descriptions as stored. A description the rules empty is dropped with the warning `cleanup removed the whole description`; an article they empty keeps its list-page description and reports `article body is empty after cleanup`. Changing a full-content feed's rules discards, in the same save, the article bodies of the stories its latest stored refresh listed, unless the feed names an **Article attribute**, and later refreshes fetch them again, 10 at a time, even from a source that answers 304; other stories keep their description and article as they were. On a feed without full article content, or one with an Article attribute, a change publishes nothing until the next refresh. Recipes without rules extract, store and export exactly the same bytes as before. Preview, **Duplicate**, recipe export and import, and the import review carry the rules, stored in the recipe as `remove`. See [content cleanup](docs/atom.md#content-cleanup).
- Set an Accept-Language for one feed under **Request settings** in its editor, such as `en` or `de-CH, de;q=0.9, en;q=0.5`, at most 10 language ranges in 128 characters. A site that offers English may then send English dates, which RSS Workshop recognizes, and some sites that refuse requests stating no language accept them. It is sent with the same requests as the feed's own User-Agent: its list page in Static HTTP mode and in Auto before any render, article pages fetched as plain HTML, previews, and the visual selector's Static HTML page. Pages that Chromium renders or FlareSolverr loads keep their browser's language preferences. There is no server-wide setting, so existing feeds still send none. Saving a value publishes nothing by itself, but a source that then answers in another language changes the feed's stories at the next refresh. On a site whose story links contain the language, such as `/de/…` and `/en/…`, or in a recipe without a link selector whose titles the source translates, every story appears once more under a new GUID, and the copies in the old language stay until `MAX_ITEMS` retention removes them. Stored article bodies keep the language they were fetched in. Recipe exports carry it as `recipe.accept_language`, the import review shows it, and **Duplicate** copies it. See [browser rendering](docs/browser.md#recipe-settings).
- Choose for each feed when it turns Quiet. **Mark as Quiet after** in the feed's editor replaces the automatic threshold with 7, 30, 90 or 365 days without a new story, or **Never**, which also leaves the feed out of `rss_workshop_feeds_quiet`. A chosen time ignores the 10-interval rule but always lasts at least one refresh interval and an hour, so a weekly feed set to 7 days is not marked Quiet before its next refresh has had the chance to find a story. It is stored in the recipe as `quiet_days` and left out for Automatic, so existing recipes, exports and the example recipes are unchanged; **Duplicate**, export and import carry it, and the import review shows it. Any other value is refused when saving, previewing or importing. Saving a change publishes nothing, but like any edit it drops the source's conditional-request validators, so the next refresh fetches the whole page once. See [quiet feeds](docs/operations.md#quiet-feeds).

### Changes

- Measure Quiet from the last new story instead of the last output change; [Upgrading from v1.2.0](#upgrading-from-v120) says what that changes. A refresh records the time when it saves a story its feed did not have saved and that retention keeps: a changed story, a story that retention removes in the same refresh, and edits do not move it, while a story that retention or history pruning removed counts as new again if a later refresh saves it again. The card reads "No new story for N days". A feed that has never saved a story, for example because its filters exclude everything, counts from its last output change instead: the latest change to its title, address or refresh interval, or, without one, its first successful refresh. `GET /api/feeds` reports the time as `last_new` beside `last_changed`, and saves accept and ignore both. Metrics add the per-feed `rss_workshop_feed_last_new_story_timestamp_seconds`, within the existing 1,000-feed bound. Reader output never reads the time, so no published byte, GUID, date, `Last-Modified` or ETag changes. See [quiet feeds](docs/operations.md#quiet-feeds) for what counts as new: a story whose link changes at every visit always does, and so does a story saved again after retention removed it, which happens at every full refresh of a page that lists more stories without a date than `MAX_ITEMS` keeps.

### Fixes

- Finish fetching full articles from sources that answer 304. A refresh fetches at most 10 article pages, and only for the stories its list page returned. A source answering `304 Not Modified` returns none, so a full-content feed listing more stories than that stopped at its first 10 bodies until the page changed. Now, while a refresh leaves stories without an article, because of that limit or its deadline, and leaves more of the listed stories with an article than before, the next refresh requests the list page without `ETag` and `Last-Modified`. Conditional requests resume after a refresh that reaches every listed story still without an article, even if some of those articles fail, or after one that adds none. Stories whose articles failed are tried again when the list page changes or after a restart. See [full article content](docs/atom.md#full-article-content).
- Stop failing Chromium feeds that fall due together. After a restart, an outage or an import, every due Chromium feed started at once, waited for one of the `BROWSER_SLOTS` inside its own `FETCH_TIMEOUT`, and the later ones failed with `context deadline exceeded` and backed off, while holding refresh slots that static feeds needed. Such feeds now wait for a free Chromium slot without failing, as FlareSolverr feeds have since v1.2.0, and other feeds are not held back; the upgrade note above says which feeds wait. A Chromium-mode feed gives its slot back once its list page is rendered, unless it renders its article pages, which it then renders one at a time in the same slot. See [Chromium capacity](docs/browser.md#capacity).

## v1.2.0 — 2026-11-07

Notifications to ntfy or a JSON webhook when a feed keeps failing or the database fails, a library you can search, filter and sort, which points out feeds that have gone quiet, a Duplicate action, and a User-Agent you can set for the server or for one feed. Story dates are read in the zone they name and with English month names, static mode reads pages in legacy encodings, FlareSolverr feeds that fall due together no longer fail, nor do refreshes cut short by stopping the app, and Pause and Resume no longer reset a feed. Sources see a new User-Agent, and some feeds change once.

### Upgrading from v1.1.1

- **The database is unchanged.** This version keeps schema 5 and opens a v1.1.0 or v1.1.1 database as it is: SQLite saves no pre-upgrade copy and PostgreSQL logs no migration. To roll back, set `RSS_IMAGE=ghcr.io/ldogg123/rss-workshop:v1.1.1-browser`, or `ghcr.io/ldogg123/rss-workshop:v1.1.1-static` with `compose.static.yaml`, or the image digest you saved; nothing needs restoring, but see the last item below for what v1.1.x does not keep. From v1.1.0, also follow [Upgrading from v1.1.0](#upgrading-from-v110), and from v1.0.0 [Upgrading from v1.0.0](#upgrading-from-v100) as well.
- **Update your checkout** (`git pull`) before recreating the container. Only the current `compose.yaml` passes the new `FETCH_USER_AGENT` and the notification settings `NOTIFY_URL`, `NOTIFY_FORMAT`, `NOTIFY_TOKEN` and `NOTIFY_AFTER_FAILURES` into the container; with an older one, Docker ignores them even when `.env` sets them. The Compose overrides and `scripts/backup.py` are unchanged.
- **Notifications stay off until you set `NOTIFY_URL`.** The new `NOTIFY_URL`, `NOTIFY_FORMAT`, `NOTIFY_TOKEN` and `NOTIFY_AFTER_FAILURES` are optional and default to off, the JSON format and 3 failures in a row, so upgrading sends nothing and adds no table. A feed that has already failed `NOTIFY_AFTER_FAILURES` times or more in a row when you turn them on is not reported as failing, since that alert goes out only as the count reaches the number, but its recovery is, so look for **Needs attention** in the library once they are on. Even while `NOTIFY_URL` is blank, startup refuses a `NOTIFY_FORMAT` other than `json` or `ntfy`, a `NOTIFY_AFTER_FAILURES` outside 1–100, or a `NOTIFY_TOKEN` without a URL. To turn them on with Compose, update your checkout as above, set them in `.env` and recreate the container with `docker compose up -d`; a native executable needs them exported. Treat `NOTIFY_URL` and `NOTIFY_TOKEN` as passwords, because a topic on a public ntfy server works as one and webhook URLs often embed a token. The app keeps both out of its logs, errors, metrics and dashboard, and they never reach the database or its backups, but `docker compose config` prints them. See [notifications](docs/operations.md#notifications).
- **Sources see a new User-Agent.** Static requests, for list pages, article pages and the visual selector, now send `RSS-Workshop (+https://github.com/Ldogg123/rss-workshop)` instead of `GoRSS/0.1 (+self-hosted feed builder)`. If a source starts refusing requests or serving different pages, set `FETCH_USER_AGENT=GoRSS/0.1 (+self-hosted feed builder)` in `.env` and recreate the container, or, for a native executable, which does not read `.env`, run `export FETCH_USER_AGENT='GoRSS/0.1 (+self-hosted feed builder)'` and start it again. A single feed can instead set its own **User-Agent**. Pages that Chromium renders or FlareSolverr loads are unaffected, but the article pages of those feeds are fetched as static HTML unless the feed renders them, so they send the new name. A source that varies its pages by User-Agent may answer the first conditional request with a full page instead of 304; feeds change only if their stories did. See [identifying requests](docs/deployment.md#identifying-requests).
- **Some feeds change once.** A story still on its source's list page changes if its description already showed the story's image, which is no longer added above it a second time, or if its source is read in static mode, declares an encoding other than UTF-8, such as windows-1252 or Shift_JIS, and the story has non-ASCII text, which was saved as `�` and is now correct. Those feeds change their bytes and `Last-Modified` once, so readers download them once; older stored stories keep what they have. On those non-UTF-8 sites:
  - Stories whose identity has non-ASCII text get a new one once, and so appear in readers a second time: the title, for a recipe without a Link selector, or a link with unencoded non-ASCII characters, which is now encoded differently.
  - A feed with **Full article content** keeps the article bodies it already fetched, `�` included, because a body is fetched once and then kept. The same holds on such sites for feeds in Chromium or FlareSolverr mode, or Auto when it renders, that do not render their article pages, which is the default: those pages were fetched as plain HTML and read as UTF-8 too, though their list pages and story identities are unaffected. To fetch them again, save the feed once with its article selector cleared, then again with it restored; later refreshes fetch 10 per refresh for stories still on the list page, and stories no longer listed show their list-page description. See [full article content](docs/atom.md#full-article-content).
  - Keyword filters with non-ASCII keywords start matching the text, so a feed can include a story it used to leave out, or the reverse. Saved stories stay unless you save the feed with the option to remove nonmatching stories.
- **Stories first saved after upgrading may be dated differently.** A date that names its zone, such as `Thu, 05 Nov 2026 10:00:00 EST`, now uses that zone instead of UTC, and a date with an English month name, such as `Nov 6, 2026`, gives the site's date instead of the time the story was first seen. A zone name that neither the recipe's time zone nor RFC 5322 defines, such as `CET` with a blank time zone, or an hour written as a name that the recipe's time zone does not use, such as `+03` or `+00`, now leaves the date unrecognized, with a `date not recognized` warning and the first-seen time; v1.1.1 read all of these as UTC, which was right only for `+00`. Set **Date settings → Time zone** to the site's zone, such as `Europe/Paris`, to have it read, or, for an hour such as `+00`, a **Go date layout** that reads it as an offset, such as `Mon, 02 Jan 2006 15:04:05 -07`. Stories already saved keep their dates and identities, so this changes no published feed. See [time zones](docs/dates.md#time-zones).
- **Pause and Resume keep a feed's state.** They now change only whether the feed refreshes: a failing feed keeps its error, failure count and the source's conditional-request validators, so after **Resume** it still shows **Needs attention** until a refresh succeeds, and a renewed failure continues its backoff instead of restarting at 2 minutes. For the same reason, pausing a failing feed no longer silences an alert on it: the feed stays counted in `rss_workshop_feeds_failing` and keeps its `rss_workshop_feed_failures` while paused. To leave paused feeds out of a per-feed alert, add `and on (id) rss_workshop_feed_enabled == 1`; for the library total, alert on `count(rss_workshop_feed_failures > 0 and on (id) rss_workshop_feed_enabled == 1)` instead. Saving the feed in the editor still clears its error, failure count and validators, as any edit does. See [pausing and resuming](docs/operations.md#pausing-and-resuming).
- **Refresh releases a feed waiting after a failed database write.** Once the database accepts writes again, **Refresh**, an editor save or **Resume** tries such a feed at once instead of leaving it to wait out its hold of up to about 17 hours. See [waiting to retry after a failed save](docs/operations.md#waiting-to-retry-after-a-failed-save).
- **FlareSolverr messages change.** Feed errors, Diagnostics and log lines for FlareSolverr failures use new messages from the next failed refresh, so update any alert that matches the old `FlareSolverr request failed`, `FlareSolverr service returned HTTP n; check its service logs`, `FlareSolverr returned an invalid JSON response`, `could not read the FlareSolverr response` or `FlareSolverr is unavailable`, which now reads `FlareSolverr is not configured on this server`. On a FlareSolverr feed, `context deadline exceeded` is replaced by messages that say what timed out: the wait for a free slot, the connection or FlareSolverr's reply. [FlareSolverr troubleshooting](docs/flaresolverr.md#troubleshooting) lists the new messages. With `FLARESOLVERR_SLOTS` above 1, a feed that renders its article pages through FlareSolverr now fetches them one at a time, so a long backlog may take more refreshes to fill in.
- **Expect some Quiet badges at first.** Feeds of sites that publish less often than every two weeks are marked [Quiet](docs/operations.md#quiet-feeds) once their output has been unchanged that long. Lengthen their refresh interval to raise the threshold.
- **Going back to v1.1.x.** v1.1.0 and v1.1.1 refuse a recipe file in which any feed has its own User-Agent (`json: unknown field "user_agent"`) and import none of its feeds, so clear the field before exporting recipes for an older server. After a rollback they ignore a stored one and send their own User-Agent for that feed, and saving the feed in their editor, or pausing or resuming it from its card, removes it. Feeds left alone keep it for the next upgrade. Rolling back also undoes this release's output fixes for stories still on their source's list page, from the first refresh that reads the page. A description that shows the story's image gets it a second time, and on non-UTF-8 sites read in static mode the text of a story whose identity this release kept shows `�` again. Those feeds change their bytes and `Last-Modified` once more, and again after the next upgrade. Stories first saved after the rollback are dated by v1.1.x's rules.

### New

- Search, filter and sort the feed library. A toolbar above the cards finds feeds by name or website, shows only the feeds with one status (Active, Quiet, Needs attention, Waiting to retry, Pending or Paused), and sorts them by name, next refresh, last success, last change or failures in a row. It works on the library the page already loads, so it adds no requests. The 10-second reload keeps the search, the selections and the keyboard focus, and the browser remembers the status and sort for the next visit. Cards also show when the feed's output last changed and how many refreshes in a row have failed. See [the library dashboard](docs/operations.md#the-library-dashboard).
- Point out feeds that have gone quiet. A refresh that finds nothing new succeeds, so a feed could stop delivering stories without ever showing a problem. A feed that keeps refreshing successfully but whose published output has not changed for 14 days, or 10 refresh intervals if that is longer, now shows a **Quiet** badge saying how long it has been unchanged. Any change to a story counts, so this is not the same as "no new stories", and a longer refresh interval raises the threshold for a site that publishes rarely. `GET /api/feeds` reports each feed's `last_changed` time and `quiet` flag, and saves accept and ignore both. Metrics add `rss_workshop_feeds_quiet` and the per-feed `rss_workshop_feed_last_changed_timestamp_seconds`, within the existing 1,000-feed bound. See [quiet feeds](docs/operations.md#quiet-feeds).
- **Duplicate** a feed from its card. The editor opens a copy with every setting, its own story filters and the same library filters, linked rather than copied, named `Copy of` and the original name shortened to fit. Nothing is saved until you save it, and the copy starts paused, with its own RSS and Atom links and no saved stories. Before, the only way was to export and import a recipe, which also turned library filters into private copies.
- Set a User-Agent for one feed under **Request settings** in its editor. It replaces `FETCH_USER_AGENT` and the built-in name for that feed's static requests: its list page in Static HTTP mode and in Auto before any render, article pages fetched as plain HTML, previews, and the visual selector's Static HTML page. Surrounding spaces are trimmed, and a value longer than 256 characters or with anything but printable ASCII is refused when saving, previewing, loading the visual selector's page or importing. Blank uses the server's default, and recipes without one are stored and exported byte for byte as before. Changing it drops the source's conditional-request validators like any recipe edit, and changes no published feed. See [browser rendering](docs/browser.md#recipe-settings) and [recipe export and import](docs/recipe-portability.md).
- Recognize English dates with a month name in element text and explicitly selected values, without a Go date layout: `5 November 2026`, `Nov 6, 2026`, `May. 5, 2026`, `Thursday, 5th November 2026 at 3:04 pm` or `5 Nov 2026 10:00 EST`. The whole value must be the date, the year must have four digits, and a weekday must match the date. A date without a time is local midnight in the recipe's time zone. Automatically detected `datetime` attributes still use only the standard formats, so they keep precedence over the element's text as before. See [month names](docs/dates.md#month-names).
- Get a message when something breaks, without Prometheus. Set `NOTIFY_URL` to an [ntfy](https://ntfy.sh) topic with `NOTIFY_FORMAT=ntfy`, or to any webhook that accepts a JSON `POST` with the default `NOTIFY_FORMAT=json`; an optional `NOTIFY_TOKEN` is sent as a bearer token. A feed is reported when its refreshes have failed `NOTIFY_AFTER_FAILURES` times in a row, and again when it recovers. Both follow the failure count stored with each feed, so a restart neither repeats an alert nor misses a recovery; a feed repaired in the editor, whose save resets that count, still reports its recovery unless the app has restarted since the alert. The database is reported when it refuses a refresh's results or the library cannot be read, at most once an hour while that lasts, and once more when the library can be read again. Events are collected for 60 seconds into one message that lists at most 20 of them, database events first, and counts the rest, so an outage that fails every feed at once sends one notification. The dashboard's status line says which format is on and, while one is, offers **Send test notification**. Messages carry feed titles, failure counts, the error a card shows with URLs removed, `PUBLIC_BASE_URL` as the link to the library and, in JSON, feed IDs, but never source URLs, reader links or story text. The address is trusted configuration like `FLARESOLVERR_URL`, so it may be on your own network, where behind Gluetun it needs a [firewall exception](docs/gluetun.md#postgresql-and-flaresolverr); environment proxies are ignored and a redirect counts as a failure. `/metrics` adds `rss_workshop_notifications_total` and `rss_workshop_notification_events_dropped_total`. See [notifications](docs/operations.md#notifications).

### Changes

- Name the project in the static fetcher's User-Agent: `RSS-Workshop (+https://github.com/Ldogg123/rss-workshop)`, replacing the prototype's `GoRSS/0.1 (+self-hosted feed builder)`. It carries no version, so later upgrades never change what sources see, and it does not reveal which release an instance runs. The new optional `FETCH_USER_AGENT` replaces it for list pages, article pages and the visual selector's static snapshot; startup refuses a value longer than 256 characters or containing anything but printable ASCII, such as a line break, and the startup log reports only whether one is set. Chromium and FlareSolverr keep their own User-Agents for the pages they load. See [identifying requests](docs/deployment.md#identifying-requests).
- `make release-test`, and so `make check` and CI, now fails when [the dependency table](docs/dependencies.md#checking-the-table) or `docs/licenses/` falls out of step with the Go modules the app links: a linked module without a row, a row pinning a version the module graph no longer selects, a missing, misnamed or leftover notice, or a copied notice that differs from its upstream file. Release source collection takes each Debian source version still listed by the current suites from Debian's regular archive, checked against the suite's `Sources` index, and falls back to Snapshot for older versions and files the archive cannot serve, so a Snapshot outage no longer blocks a release whose packages are current.

### Fixes

- Pause and Resume on a feed card no longer send the card's whole copy of the feed. A card drawn before an edit in another tab could undo that edit; if the edit corrected an article selector, the article bodies fetched with the corrected selector were deleted, and a reverted title or interval rewrote the published feed. Every pause and resume also threw away a refresh in progress. They now use their own request, `POST /api/feeds/{id}/enabled`, which changes nothing readers see. Older clients and scripts that pause by saving the feed, including ones that send back a feed object from `GET /api/feeds`, keep working.
- An editor left open no longer re-enables a feed paused from its card. A save keeps the feed's current setting unless **Refresh automatically** was changed.
- **Refresh**, saving a feed in the editor, and resuming it now retry a feed held after the database refused a refresh, for example on a full disk. Such a feed used to wait out its hold, up to about 17 hours, while Refresh reported it as queued and the dashboard showed it as due and healthy. A retry that fails again waits twice as long as the last one. The card now says **Waiting to retry**, feed listings report `"held": true`, and the new `rss_workshop_feeds_held` metric counts these feeds; `rss_workshop_feeds_due` keeps its meaning and still includes them.
- A refresh thrown away because its feed was edited while it ran is now logged as `refresh discarded` at info level, instead of `refresh finished` with an item count or `refresh failed` with a failure count, although nothing from it was stored. A feed deleted during its refresh is logged the same way and is no longer held; before, it was logged at error level as if the database had refused the write.
- A refresh cut short by stopping or restarting the app is no longer stored as a failure. A restart that cut a refresh short before its stories were extracted gave a healthy feed an error such as `context canceled` on its card, a failure in a row and a backoff. Such a refresh is now discarded, logged as `refresh discarded` with `reason="server stopping"`, and leaves no run in Diagnostics, so the feed is still due and refreshes when the app starts again. A refresh that runs out of its own time still counts as a failure, and one that had already succeeded is still stored.
- **Refresh** answers 500 when the database cannot be read, and **Reset feed links** when it cannot be written, instead of 404 as if the feed did not exist.
- Read the time zone a date names. An RFC 1123 date such as `Thu, 05 Nov 2026 10:00:00 EST` was stored as 10:00 UTC, five hours early, because a zone name the recipe's time zone does not define was given a zero offset: with a blank time zone every US zone name was hours off, any made-up name was accepted as UTC, and `GMT+3` was read as UTC. A zone name now takes the meaning the recipe's time zone gives it, so `CST` stays China Standard Time under `Asia/Shanghai`, and otherwise the meaning RFC 5322 gives it (`UT`, `GMT`, `EST`, `EDT`, `CST`, `CDT`, `MST`, `MDT`, `PST`, `PDT`). `GMT+3` is read as +03:00 and `GMT+0` as UTC, and any other name leaves the date unrecognized rather than guessing. The same rules apply to a Go date layout containing `MST`. RFC 1123 dates may also have a one-digit day and leave out the seconds. See [time zones](docs/dates.md#time-zones).
- Decode pages in static mode the way browsers do. A site served in windows-1252, ISO-8859-x, Shift_JIS, EUC-KR, windows-1251, UTF-16 or another encoding browsers support was read as UTF-8, so static mode, and Auto when it did not render, published its accented and CJK characters as `�`, while Chromium mode showed its list pages correctly. The encoding now comes from a byte order mark, the `Content-Type` charset or a `<meta>` charset in the first 1,024 bytes, for list pages, article pages and the visual selector's static snapshot alike. A page that declares nothing or an encoding browsers do not support is read as UTF-8 as before, and so is a page that declares a legacy encoding but whose text is mostly valid UTF-8, the usual sign of a site that moved to UTF-8 and kept its old declaration. The 4 MiB page limit now also applies after decoding, as it already did in Chromium mode, so a page close to that size in an encoding whose characters take more bytes in UTF-8, such as Shift_JIS, can now be refused. See [fetch modes](docs/browser.md#recipe-settings).
- Stop showing a story's image twice when its list-page description already shows it, as happens when the Description selector covers the whole card. The image is now left out when the description has an image with exactly that address; a link to the image, as lightboxes use, or a different size of it still gets the image shown above. RSS `media:content` and the Atom enclosure are unchanged.
- Stop failing FlareSolverr feeds that fall due together. The scheduler started every due feed at once, up to `STATIC_WORKERS`, against FlareSolverr's single default slot, and each refresh waited for that slot inside its own deadline, so after a restart, an outage or an import the later feeds failed with `context deadline exceeded` and backed off. RSS Workshop now starts only as many FlareSolverr refreshes as there are free slots, counting slots still held after an interrupted request. The rest stay due and start oldest first as slots free up, with no failure recorded, and feeds in other fetch modes are not held back. A refresh hands its slot on once its list page is solved, unless it renders its article pages through FlareSolverr, which it then fetches one by one. A FlareSolverr preview or visual-selector page load that finds every slot in use answers `FlareSolverr is busy` at once instead of waiting out its deadline. It has no claim on the next free slot: while FlareSolverr feeds are due, as after a restart, an outage or an import, each freed slot goes to them first, so previews and page loads can stay busy until those feeds have refreshed. See [FlareSolverr capacity](docs/flaresolverr.md#capacity).
- Name what failed when FlareSolverr cannot be reached. Every connection problem used to read `FlareSolverr request failed; check the service address, connection, and timeout`, and any other service's reply only `FlareSolverr service returned HTTP n`. Previews, the visual selector, feed cards, Diagnostics and the log now name the step: a DNS lookup, a refused or timed-out connection, no network route, a connection that failed before the request was sent (usually TLS), an address that is not the FlareSolverr `/v1` API, a reply from something other than FlareSolverr, a dropped connection, no reply before the deadline, or a wait for a free slot. The messages are fixed text and never include the service address, the source URL or the reply. A request that never connected now frees its slot at once instead of holding it for the whole solver timeout. [FlareSolverr troubleshooting](docs/flaresolverr.md#troubleshooting) says what to check for each message.
- Point the editor's "FlareSolverr is not configured" hints to the setup guide. The advice now holds for Docker Compose, where the container must be recreated with `docker compose up -d` because `docker compose restart` keeps its old environment, for native executables, which do not read `.env`, and for installs sharing Gluetun's network, where `127.0.0.1` is the right address.
- Stop a feed refreshing twice in a row when its refresh ended while the scheduler was reading the feed list. That list still showed the feed due, so it started again at once, which with FlareSolverr spent a solve ahead of feeds waiting their turn.

## v1.1.1 — 2026-11-05

Security updates for the Go runtime, its modules and the browser image, a WebRTC leak closed in browser mode, a selector failure that could stop the server, and more story images found. PostgreSQL users should check `DATABASE_URL` before upgrading.

### Upgrading from v1.1.0

- **PostgreSQL: check `DATABASE_URL` first.** The newer driver reads it the way PostgreSQL's own client library does, so the first `@` ends the credentials. Percent-encode an `@` in the user name or password as `%40`, or startup stops with `percent-encode @ in the user name or password as %40`. Inside a query value, encode `=`, `&`, `%` and spaces, as in `options=-c%20search_path%3Drss`, and write every parameter as `key=value` with no empty ones such as `&&`, or startup stops with `invalid PostgreSQL connection configuration`. A `+` in a query value is now a literal plus rather than a space, a parameter given twice takes its last value, and in a URL with several hosts each host needs its own port. v1.1.0 reads an encoded URL the same way, so change it before upgrading. URLs written as [PostgreSQL setup](docs/postgresql.md#existing-postgresql-server) describes, including its generated hexadecimal password, need no change.
- **The database is unchanged.** This version keeps schema 5 and opens a v1.1.0 database as it is: SQLite saves no pre-upgrade copy and PostgreSQL logs no migration. To roll back, set `RSS_IMAGE=ghcr.io/ldogg123/rss-workshop:v1.1.0-browser`, or `ghcr.io/ldogg123/rss-workshop:v1.1.0-static` with `compose.static.yaml`, or the image digest you saved; nothing needs restoring. From v1.0.0, also follow [Upgrading from v1.0.0](#upgrading-from-v100).
- **No configuration changes.** The Compose files, `.env` settings and `scripts/backup.py` are as v1.1.0 shipped them, so a v1.1.0 checkout runs the new images. Update it for the corrected guides or to build from source.
- **Some feeds change once.** A story still on its source's list page changes if it gains a lazy-loaded image or a corrected `srcset` image, and a full article changes if it showed its image twice. Those feeds' bytes change once, so readers download them once. Story identities and publication dates do not change, so no reader sees a story twice.

### Security

- Update Go to 1.27.3 and the Go modules the app uses, fixing 15 reachable vulnerabilities reported by `govulncheck`: in the standard library's HTTP/1, HTTP/2, TLS, certificate, MIME and `html/template` code, and in HTML parsing and rendering in `golang.org/x/net`.
- Update the browser image to Chromium 156 and a current Debian base. Debian had removed the previously pinned Chromium, so that image could no longer be built from source.
- Stop pages that Chromium renders, in browser mode, Auto's fallback or rendered articles, from sending WebRTC UDP past the proxy. The switch meant to disable it is not in Chromium's regular build, which ignores switches it does not know, so a rendered page could send STUN packets carrying text of its choosing to any routable address and port, including ones the outbound policy rejects. The switch Chromium reads is now set as well.
- Correct the browser guide, which said WebSocket URLs were blocked through DevTools. They never were: a rendered page can open a WebSocket, and it is confined by the proxy's rule of validated destinations on port 443 and its limits, which held throughout. The patterns that had no effect are removed.

### Fixes

- A page that the XPath library cannot evaluate no longer stops the server. On the bundled antchfx/xpath, comparing a non-number with a number, such as `//article[@data-score > 1]` on a page with `data-score="n/a"`, or a `substring()` range past the end of a short value, panics. During a refresh or an article fetch, including the editor's article preview, that panic stopped the whole process and every other feed with it. Such a refresh now fails like any other: the feed keeps its saved stories, backs off, and shows `selector evaluation failed` with the field's name. A failed article keeps its list-page description. A list preview reports the same error instead of dropping the connection. The log records the field and a short stack, but not the page value or the selector, since either can hold a URL. In v1.1.0 the crash could write that value to the container log, so check older logs before sharing them. See [the visual selector limits](docs/visual-selector.md#limits) for selectors that avoid the failure.
- Find a story's lazy-loaded image when a lazy-loading script keeps its real address in an attribute of its own. When `src` holds only a placeholder, such as an inline `data:` image, and the usual attributes give no address, detection now tries a fixed list of attributes used by common lazy-loading scripts and CDNs, such as `data-original` and `data-webp`, listed in [the visual selector guide](docs/visual-selector.md#manual-selectors-and-images). Images that already resolve keep their address. A feed that gains an image changes its published bytes once, so subscribers refetch it.
- Read `srcset` the way browsers do, except that addresses joined by a bare comma still separate where an address visibly starts or an image file ends at the comma. Commas inside a candidate, as in a CDN address containing `w_400,h_300` or an inline `data:` image, were treated as separators and could publish a broken address; stories still on the source's list page get the correct image at the next refresh, and older stored stories keep the address they have. A `srcset` candidate too long to publish now counts as unusable, so it no longer fails the page and is left out of descriptions and articles.
- Stop full-article feeds from showing a story's image twice when its address contains `&` or `'`, as CDN addresses with a query such as `?w=640&q=75` do. The check for an image the article already shows compared the address with the article's markup, where those characters are escaped, so it never matched; the image detection above made this happen to some lazy-loaded thumbnails too. Affected feeds change their bytes and ETag at the first request after upgrading. Their `Last-Modified` and Atom `updated` times stay as they were, so a reader that sends only `If-Modified-Since` keeps its copy until the feed next changes.

## v1.1.0 — 2026-09-16

Reusable filters, safer upgrades, and feeds that stop changing when nothing in them has. See [upgrades](docs/operations.md#upgrades) before installing over an existing deployment.

### Upgrading from v1.0.0

- **Update your checkout first** (`git pull`). The current `compose.yaml` passes the new `UPGRADE_BACKUP` setting into the container, and the current `scripts/backup.py` reads schema 5 and leaves the automatic copies out of its backups; the v1.0.0 versions do neither.
- **The database moves to schema 5**, in one transaction, the first time this version starts. v1.0.0 cannot open the result, so rolling back means restoring a copy taken before the upgrade.
- **SQLite takes that copy for you.** Before upgrading, the app saves a verified copy to `backups/pre-upgrade-schema-4-<time>` in the data directory and names it in the log. It needs free space about the size of the database, or startup stops before upgrading; the copies are never deleted automatically. To roll back, stop the app, `sudo python3 scripts/backup.py restore` the copy into a new directory, point `RSS_DATA_DIR` at it and pin `RSS_IMAGE` to v1.0.0. The copy sits on the same disk, so keep an off-host backup too. See [automatic copy](docs/operations.md#automatic-copy-before-an-sqlite-upgrade).
- **PostgreSQL gets no automatic copy.** Take a `pg_dump` before upgrading; the app logs a warning when it migrates.
- **RSS readers refetch once.** The RSS `generator` no longer carries a version, so each RSS feed's bytes change once with this upgrade and not again because of later version bumps. Atom feeds are byte-for-byte unchanged by the upgrade.

### Filter library

- Add a **Filter library**: save story filters once and select them in any feed. Feeds use library filters by reference, so editing one updates every feed using it, with the same optional cleanup of saved stories as a feed edit. A feed's own rules and its library filters combine, and the existing filter limits apply to the combination. Recipe exports copy the combined rules so files stay importable anywhere. This adds database schema 5; take a backup before upgrading, because v1.0.0 cannot open the upgraded database.

### Upgrades you can undo

- Save a verified copy of an SQLite database in `backups/` inside the data directory before upgrading its schema, because an older release cannot open the upgraded database. The copy uses the backup utility's format, so `scripts/backup.py verify` and `restore` accept it. If it cannot be saved, the app stops before upgrading the database; `UPGRADE_BACKUP=false` skips the copy. A restart after a failed upgrade reuses an identical copy instead of saving another. PostgreSQL upgrades log a warning instead, since the app cannot run `pg_dump`.
- `scripts/backup.py backup` now keeps only the database and its write-ahead log from the stopped container, instead of copying all of `/data` into temporary space.

### Fewer full downloads for readers

- Stop rewriting every feed on every refresh. Published dates and `Last-Modified` came from the time of the last refresh, so a refresh that changed nothing, even one where the source answered 304, gave each feed new bytes and a new ETag, and a reader polling at the advertised `ttl` almost never received a 304. Feeds and stories now record when their published output last changed, which moves only when a story, the feed's title, URL or interval, or its saved history actually changes, including edits to a paused feed. Upgrading keeps every published date as it was. The RSS `generator` no longer includes the version, so RSS subscribers download each feed once after this upgrade and not again on later ones; Atom subscribers are unaffected.

### Fixes

- Fix SQLite foreign keys switching off after an interrupted read. The settings were applied once, and a reader disconnecting mid-response could leave the app on a replacement connection without them; deleting a feed then left its stories, runs and filter links behind. Settings now apply to every connection, and startup removes rows left by feeds that were already deleted, which otherwise make the backup utility and the pre-upgrade copy refuse the database.

## v1.0.0 — 2026-09-12

First stable release. RSS Workshop turns pages that publish no feed into RSS and Atom feeds you keep, and 1.0 is the point at which its upgrade path, configuration surface and reader URLs become commitments rather than implementation details. See [upgrades](docs/operations.md#upgrades) before installing over an existing deployment.

### Upgrading from v0.2.0

- **Take a backup first.** Starting this version migrates the database to schema 4 in a single transaction. Every released schema upgrades directly, but an older release cannot open a newer database, so rolling back needs a backup taken *before* the upgrade. See [backup and restore](docs/operations.md#backup-and-restore).
- **Readers refetch once.** Published feeds carry more than they did, so every feed's bytes change once and subscribed readers fetch a full copy on their next poll. Stories keep their identities and publication dates, so nobody sees a duplicate.
- **Container logs now rotate**, at three 10 MiB files per service. `docker compose logs` reaches back only as far as the retained files.

### Feeds readers actually want

- **Full article content.** Follow each story's own link, extract the article body, and publish that instead of the list page's one-line teaser. Off by default and configured per feed. Article pages are fetched with the same guarded fetcher as list pages, at most 10 per refresh so a long feed fills in over several cycles, and an article that cannot be fetched keeps its teaser rather than dropping the story or failing the refresh.
- **Better published feeds.** RSS keeps the article in `description` and repeats it in `content:encoded`; Atom carries the list-page description as `summary` and the article as `content`. The extracted image is published as `media:content` and as an Atom enclosure, where readers look for a thumbnail, and is no longer repeated when the article body already contains it. The RSS channel gains `atom:link rel="self"`, `ttl`, `lastBuildDate` and `generator`.
- **Conditional requests.** Reader responses honour `If-Modified-Since` alongside the existing ETag, so a reader polling from several devices costs validators rather than full copies.
- **OPML export.** Download a subscription list of every feed and import it into your reader in one step. It contains every private reader link, so it requires an admin session and is never cached.

### Knowing when something breaks

- **Log levels.** `LOG_LEVEL` selects `debug`, `info`, `warn` or `error`, and `LOG_FORMAT` switches to JSON for a log collector. The startup line summarizes the running deployment, failed refreshes report their reason and feed, rejected sign-ins are reported with their remote address, and shutdown is logged.
- **Prometheus metrics.** Setting `METRICS_TOKEN` enables `/metrics`, scraped with that token as a bearer credential; blank leaves the endpoint returning 404. Per-feed series carry item counts, consecutive failures and last-success timestamps, so an alert can name the feed that broke.
- **A failed database write no longer hammers the source.** Such a refresh rolls back the feed's schedule along with everything else, so the source was refetched on every scheduler tick for as long as writing failed, while the log reported success. The feed now backs off, and the failure reports its reason.
- **Retention is visible.** `MAX_ITEMS` applies to stories already saved, so lowering it permanently deletes the excess at each feed's next refresh. That now appears in the log and is documented as destructive.

### Running it

- **Reverse proxy support.** `compose.proxy.yaml` and a [guide](docs/reverse-proxy.md) for a proxy running in Docker, which cannot reach the default loopback publication.
- **Container log rotation**, configurable through `LOG_MAX_SIZE` and `LOG_MAX_FILES`.
- **Stable image aliases.** `latest` and `latest-browser` include Chromium; `latest-static` selects the lightweight runtime. Compose follows these aliases, with version and digest pins still available.
- **Direct upgrades from every released schema**, with frozen per-backend fixtures and tests comparing all saved feed, item and run data across upgrade and reopening. Backups support schemas 1 through 4.

### Editor and examples

- **Full article content is inspectable and repairable.** Previews show the fetched body, so a selector matching the wrong block is visible before saving, and changing or clearing the selector discards the stored bodies so later refreshes fetch them again.
- **New example recipes.** The previous examples targeted five real news sites that all publish their own feeds, extracted only a title and link, and two relied on generated class names that change whenever those sites deploy. They are replaced by a demo site included in the repository, with recipes covering every field, CSS and XPath, and filtering with full article content. A test imports each example and extracts from that site.
- **Reorganized documentation.** The README follows install, first feed, and diagnosing a broken one, with installation variants collected below; `.env.example` is grouped by purpose. Screenshots are refreshed and now include full article content and per-feed diagnostics.

### Internal

- Security headers applied to every response are pinned by a test; the content policy is the second layer behind sanitization for extracted markup and previously had no coverage of its own.
- A refresh no longer loads every stored article body to decide which article pages to fetch.
