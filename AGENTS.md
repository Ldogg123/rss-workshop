# Working on RSS Workshop

This file applies to the entire repository. Use `rss-workshop` for the Go module, executable, Compose service/project, and image names; use **RSS Workshop** in the UI and prose.

## Setup

- Run commands from the repository root. Use the Go version declared in `go.mod`, Python 3.11 or newer (standard library only), and Make. Race tests also require a C compiler.
- Docker Engine and the Compose plugin are needed for container checks. Use Compose 2.24.4 or newer because the overrides use `!reset` and `!override`. Check Docker access before running container tests; `DOCKER='sudo docker'` works with Make's container targets when necessary.
- No Node install or frontend build is needed. Templates, CSS, JavaScript, and database schemas are embedded in the Go executable. Rebuild/restart the server after changing them.
- Check the existing setup before installing tools, recreating services, or changing configuration. `make GO=/absolute/path/to/go ...` supports an existing Go installation outside `PATH`.

```sh
go mod download
make build                 # bin/rss-workshop
make check                 # formatting, race tests, vet, Python checks, native smoke
```

For a disposable native development instance, use a separate port and data directory:

```sh
ADMIN_PASSWORD=local-development-only \
PUBLIC_BASE_URL=http://localhost:8081 \
LISTEN_ADDR=127.0.0.1:8081 \
DATA_DIR="$(mktemp -d)" \
DATABASE_URL= \
make run
```

That password is only for local development. The native process reads exported environment variables; it does **not** load `.env`. Compose loads `.env` automatically. Do not replace an existing `.env` with the example or reuse an operator's database for tests. See [deployment](docs/deployment.md) for the maintained Compose commands and configuration reference.

## Behavior to preserve

- Serialization never reads the clock: every value published comes from stored state, so unchanged stories produce identical bytes and a polling reader keeps receiving 304. Published dates and `Last-Modified` come from `last_changed` on feeds and items, never from observation times such as `last_success` or `last_seen`, which move on every refresh. Any write that changes published output must move the feed's `last_changed` strictly forward (the merge, retention, edits to title, URL or interval, cleared article bodies, history pruning, library filter pruning), and a write that does not must leave it alone; a story inserted and removed by retention in the same refresh was never published, and an interval edit counts only when its whole minutes of `ttl` change. RSS and Atom share this time, and configuration such as `PUBLIC_BASE_URL` is not tracked by it; both are documented trade-offs in docs/atom.md, and the ETag still reflects them. The RSS `generator` carries no version, so an upgrade alone never rewrites a feed. RSS keeps the full article in `description` and repeats it in `content:encoded`; Atom splits the list-page description into `summary` and the article into `content`. The extracted image is published as media and inline, but only once in the body. Changing any of this rewrites every feed and forces every subscriber to refetch, so batch such changes rather than shipping them one at a time.
- Reader requests serialize saved items; they must never fetch or render the source. Failed or empty extraction preserves previously saved output. Publication dates and GUIDs remain stable across refreshes, including relative-date estimates. Date parsing never guesses what a zone name means: it reads `UTC`, a `GMT` offset such as `GMT+3`, a name the recipe's time zone uses and the names RFC 5322 defines, and any other name leaves the date unrecognized, so the story keeps its first-seen time and a warning instead of Go's invented zero offset, which can be hours wrong. Automatically detected `datetime` attributes keep to the standard formats, and month names are read only from element text and explicitly selected values, so the element's text can still win over a non-standard attribute.
- `MAX_ITEMS` is retention over everything stored, not a cap on new stories, so lowering it deletes saved history at the next refresh. It is the only irreversible effect available through configuration: report it in the log when it removes rows, and keep it documented as destructive.
- A refresh whose result cannot be stored has changed nothing, including the feed's schedule, so the scheduler holds that feed in memory with its own backoff. Without it the source is refetched every tick for as long as the database is unwritable. Such a refresh must report the failure and must not report success. A manual Refresh, an editor save and a resume have just written to the database, so each lifts the hold through `Scheduler.Retry`, which keeps the hold's failure count: a write that fails again waits twice as long instead of starting over. A result thrown away because its feed was edited (`ErrStale`) or deleted (`ErrDeleted`) while it ran, or because it failed after the server began stopping, is not a failure: it stores nothing, moves no failure count, raises no notification and logs `refresh discarded` at Info with the reason, and a deleted feed is not held. Otherwise a restart could add a failure and a backoff to healthy feeds. A refresh's own deadline is still the source's failure, and a result that succeeded before the shutdown is still stored. A tick never starts a feed whose refresh ended after the tick read the feed list, because that list predates the schedule the refresh saved and still shows the feed due.
- Every Compose service rotates its container log. Docker retains logs until the disk fills, so an unbounded service log is a denial-of-service vector for anything that can make the app write lines. Keep the cap when adding a service.
- `/metrics` is disabled unless `METRICS_TOKEN` is set, and then requires that token as a bearer credential; an admin session is deliberately not sufficient, because a scraper cannot hold one. Series may name feeds but must never carry reader links, source URLs, or story content, and per-feed series stay bounded. Logs follow the same rule: feed titles are allowed, source URLs, reader tokens, passwords and cookies are not.
- Health notifications are optional and configured only by environment (`NOTIFY_URL`, `NOTIFY_FORMAT`, `NOTIFY_TOKEN`, `NOTIFY_AFTER_FAILURES`), so the endpoint never reaches the database or its backups. The URL and token are secrets: neither appears in a log line, an error, metrics, the dashboard or a message, so delivery failures are reduced to fixed reasons (Go's `*url.Error` quotes the URL) and configuration errors name the setting, never its value. Like `FLARESOLVERR_URL` the endpoint is trusted configuration outside `ALLOW_CIDRS`, but delivery ignores environment proxies and treats a redirect as a failure. Feed events are edges of the stored failure count, so notifications need no stored state of their own and a restart neither repeats an alert nor misses a recovery: `failing` when a stored failure brings the count to exactly the threshold, `recovered` on a success from at or past it or after a `failing` this process sent. `not_saved` and `db_unavailable` live in memory and go out at most once an hour while the problem lasts. Discarded refreshes and Chromium or FlareSolverr admission waits raise nothing. `Notify` must never block a refresh: keep the separate bounded queues for feed and server-wide events, the single coalescing worker, the per-attempt and retry limits, the 10-second spacing of test messages and the bounded flush after the scheduler stops. Messages follow the metrics rule; titles and errors stay on one line and only in bodies, and ntfy headers carry only fixed values and `PUBLIC_BASE_URL`, because a title with a line break would add headers of its own.
- Full article content is optional and per feed. Article pages go through the same guarded fetcher and destination validation as list pages; rendering them is an explicit opt-in because the browser pool is shared. Keep the per-refresh article cap, the fetch-once-then-recency rule and the bounded preview sample. A 304 lists no stories, so a backlog behind one would never drain: a full-content feed's static list request drops its validators once after each start, and after a stored successful refresh that left stories without a body unqueued (cap or deadline, including a story handed to a worker after the deadline) and raised the number of listed stories stored with one. Keep that flag in memory, the stored validators untouched, failed refreshes and previews out of it, and deleted feeds forgotten. Requiring that number to grow is what stops articles that always fail, and stories retention removes, from disabling conditional requests for good; undated stories beyond `MAX_ITEMS`, which every full request stores again as the newest, still change such a feed at each one. A failed article keeps the list-page description and must never drop the story or fail the refresh. Fetched bodies are stored separately from that description so re-extracting the list page each refresh still updates late-published images without discarding retrieved articles. Article pages must never change an item's identity, date or link.
- Changing or clearing a recipe's article selector discards that feed's stored article bodies in the same transaction as the edit, because a body is otherwise fetched once and preserved by every later merge. The editor is the repair path for a selector that captured the wrong block; an unrelated edit must keep correct bodies. Previews display the fetched body so the mistake is visible before saving. Changing the cleanup rules (`remove`) of a body not read from an attribute is the one partial clear, and so, defensively, is a selector type change that keeps rules (none is valid in both CSS and XPath, and a feed source's rules are CSS like a CSS page's): it discards only the bodies of the stories listed by the latest stored refresh that read the page, because no other story's article would be fetched again. That is the newest run that succeeded without a 304. If it stored no story (all filtered out, or an empty feed source), nothing is cleared; otherwise the stories of the latest merge are, chosen by the feed's maximum `last_seen`, which a 304 does not move; with no such run among the 50 kept, the latest merge stands in. The save reads the stored recipe once and moves `last_changed` only when rows change.
- Schema 4 stores fetched article bodies. Its merge replaces a stored body only when a refresh actually fetched one; an empty value means "not fetched this time", never "the article is empty".
- The OPML export lists every feed's private reader link, so it stays behind authentication, uncached, and out of recipe exports. Its `xmlUrl` values must remain the links the reader routes actually serve.
- Reading per-feed diagnostics must not fetch or queue a source. Keep the latest 50 refresh runs per feed; previews do not write history. Preserve legacy summaries, bounded/redacted traces, and plain-text expected/received field samples. Missing optional fields must not reject otherwise valid items. The library listing, which the dashboard polls every 10 seconds, and `/metrics` add no query per feed. State that only the listing sets (`held`, `quiet`) stays on `model.Feed`, as the stored times `last_changed` and `last_new` do, because saves and previews refuse unknown fields: they accept and ignore it, so a feed taken from the listing can be sent back, and only the store moves those times.
- Quiet means no new story. `Feed.IsQuiet` reads only the feed row and measures from `Feed.QuietSince`: `last_new`, or `last_changed` for a feed that has never stored a story. Changed stories therefore never reset it, nor do edits once the feed has stored a story (until then a title, URL or interval edit moves `last_changed` and resets it). A feed source needs no case of its own: an entry is new when its identity is first stored, and an empty feed stores none. A held feed is never quiet, because its latest refresh was never stored. The threshold is `model.QuietAfter` unless `recipe.quiet_days` sets one, which still waits one interval and `model.QuietMargin`, so a feed is never Quiet before its next refresh could store a story. `quiet_days` is omitted when 0 and accepts only `model.QuietNever` and `model.QuietDayChoices`, the editor's options, so an editor save keeps any stored value.
- Selector libraries panic on ordinary page content (antchfx/xpath does on a numeric comparison with a non-number, or a short `substring()`), and refreshes and article workers run on bare goroutines, where a panic stops the server. `extract.RunAt` and `extract.Article` recover and return `ErrSelectorFailed`, which follows the usual failure rules: a refresh fails and backs off, an article keeps its list-page description. Evaluate selectors only inside those two functions. The panic's value quotes the page and the selector can hold a URL, so neither goes into the error or the log. Cleanup rules are selectors too, in the language `articleType` gives: `clean` runs them in those two functions only, before sanitizing, on a detached copy of the selected block, which they can never remove, and never on an attribute result, and names them only as `cleanup rule N`. A rule must stay on one line, because the editor shows one per line. Without rules extraction stays byte-identical (the golden test). A description they empty is published empty with its own warning; an article they empty fails, but a body that showed nothing before cleanup is stored as before, or video posts would be refetched every refresh.
- Automatic image detection must not change an image that already resolves, because a changed address rewrites published feeds. The exception is `srcset`, which follows browsers apart from addresses joined by a bare comma, as the changelog describes. The fallback runs only after the usual attributes give no address, on an `img` element, and only for the story's own image, so descriptions cannot grow from it. It reads a fixed list of lazy-loading attributes and only the first matched element, since an attribute's name does not reveal its purpose and a later image is as likely to be an avatar or an icon. Add an attribute to the list and to docs/visual-selector.md rather than inferring from names, and keep the value check strict; publishing no image is better than publishing a video, a link or a tracking flag as one. A value too long to publish there is unusable, not a failed page. An explicit attribute reads only what the operator named, from the first match, and needs an image selector.
- Filtering happens after required-field validation. Zero included items with valid extracted stories is successful and must not trigger Auto fallback or error backoff. Preserve existing history by default; only the explicit save option may prune nonmatching stored stories, atomically with the recipe edit. Never import that one-time option. Keep the keyword/tree/recipe-size bounds, bulk entry, and identical preview/refresh matching.
- Library filters are shared by reference: a feed stores the ordered IDs it uses beside its recipe, never copies of their rules. Every path that evaluates filters (preview, refresh, history pruning, export) uses the feed's own rules merged by `filter.Combine`, and the ordinary filter bounds and editor size limit apply to that merged set. Editing a library filter validates, invalidates (version and conditional validators) and optionally prunes every feed using it, in one transaction; a save that omits `filter_ids` keeps a feed's links. Deleting a filter in use is refused. Exports carry merged rules, not IDs, so recipe files stay self-contained.
- Static mode must work in the minimal image without Chromium or FlareSolverr. Optional modes share extraction, sanitization and persistence. Keep FlareSolverr an explicit opt-in; its remote network boundary differs from the local guarded fetcher. A job that waits for a FlareSolverr slot spends its own deadline, so the scheduler admits a FlareSolverr refresh, preview or page load only while a slot is free, counting admitted jobs and slots still held after interrupted requests (`Client.Cooling`). A due feed over that cap stays due without a failure or backoff; a preview or page load gets `ErrSolverBusy`, which matches `ErrBusy` and so answers 503; a job gives its admission back after its last page through the solver, and articles rendered there go one at a time. FlareSolverr errors name the failed step in fixed text, never the endpoint, the source URL or the reply, because Go's transport errors quote the endpoint and these errors reach cards, Diagnostics, logs and notifications.
- `fetch.Client.Fetch` is the one static path for list pages, article pages fetched as plain HTML, previews and the static snapshot, so they decode and identify themselves alike. It decodes a page to UTF-8 only from a byte order mark, a `Content-Type` charset or a `<meta>` (for a feed source's list, the XML declaration) in the first 1024 bytes, holding the result to the same 4 MiB. It keeps the exact bytes of a page that declares nothing, UTF-8 or an encoding browsers do not support, or that declares a legacy encoding but is mostly UTF-8. A decoding change alters stored text and so published feeds. It also gives a new identity to every story keyed by its title (a recipe without a Link selector) or by a link that holds non-ASCII text, which breaks GUID stability and shows readers those stories twice: batch it like a serialization change and describe it in the changelog's upgrade notes, as v1.2.0 does. It sends the recipe's `user_agent`, else `FETCH_USER_AGENT`, else `fetch.DefaultUserAgent`, which like the RSS `generator` carries no version, so an upgrade alone never changes what sources see. Chromium and FlareSolverr send their browser's own: Chromium's must agree with its client hints, and FlareSolverr's API has no per-request User-Agent. Both settings pass `fetch.CheckUserAgent` (at most 256 bytes of printable ASCII, so no header injection); handlers trim first, and `Fetch` refuses a value that is not already valid rather than send it altered. The value is never logged, put in metrics or diagnostics, or repeated in an error. Changing it is a recipe edit that leaves `last_changed` alone, and a blank one is omitted, so the recipe stores and exports the bytes v1.1.x accepts; v1.1.x refuses a recipe file that carries one. v1.1.x opens the database and ignores a stored one, dropping it on its next save, Pause or Resume. That changes only what the source sees, so unlike filters (schema 3) it needed no schema change; a recipe field whose absence would change published output still needs one. A recipe's `accept_language` travels beside `user_agent` through `requestContext` alone, so every static request made for the feed carries both, previews, snapshots and article pages included, while Chromium and FlareSolverr keep their own. It passes `fetch.ValidateAcceptLanguage` when saved and again in `Fetch`, is stored and sent only when set, has no server-wide default, and never appears in errors, logs or metrics. Unlike `user_agent` it can change published text, so it relies on schema 6's gate.
- A feed source (recipe type `feed`) reads an RSS, RDF or Atom document in place of cards: no item or field selectors, Static HTTP only, no rendered articles, and a CSS article selector and cleanup rules through `articleType`, which validation, `clean` and `Article` share. Only its list request in `scheduler.extract` carries `fetch.AsFeedSource` (feed `Accept`, XML decoding); article pages keep the pinned HTML `Accept`. `RunAt` maps entries inside its recover through the same `add` step as cards, so limits and filters agree in preview and refresh. Identity is the guid, Atom id or `rdf:about`, then the link, then the title, which is why a saved feed keeps its source: the editor locks it, and the save refuses a switch between a web page and a feed source (`store.ErrSourceSwitch`, a 400 that points to Duplicate) from its one read of the stored recipe, before any write. encoding/xml quotes the document in its errors, so a parse failure names a line only; one unreadable entry fails the refresh and keeps history, and a well-formed empty feed succeeds with zero stories, so it lists none and a cleanup edit after it clears no article body. An element after the root ends reading, but a stray end tag inside the feed must still fail it, never cut it short. Entry mapping decides published titles and descriptions, so batch changes to it like serialization changes: an RSS title is markup only when unescaped or when it closes a tag and every tag is a common inline element, so a literal `<` survives, and a description over 256 KiB or showing nothing once sanitized gives way to the next candidate. Cleanup rules run on each candidate before it is judged, so one they empty gives way too, and the description is dropped with the cleanup warning only when they emptied every candidate that showed something. The image fallback reads what the rules leave, since a feed source has no Image selector, but an untitled entry's title, and so a title-hash identity, is read before cleanup: rules never re-key or skip an entry.
- Plain `compose.yaml` downloads the published Chromium image with its sandbox and resource limits. `compose.static.yaml` selects the smaller published runtime and clears browser-only settings. With `RSS_IMAGE` blank, the browser tracks `latest` (also `latest-browser`) and static tracks `latest-static`. Operator defaults use `pull_policy: always`; build overrides use `build`, and private smoke fixtures use `never`. An explicit tag or digest must match the runtime. Container checks must exercise aliases, pins, pull policies and local builds.
- `compose.proxy.yaml` is for a reverse proxy running in Docker: it stops publishing a host port and joins an existing external network, because a proxy container cannot reach the host's loopback. Keep the app on its default network too, or an optional database becomes unreachable, and keep the database off the proxy network.
- Operator Compose files contain no local build. Development explicitly adds `compose.build.yaml` for Chromium, or `compose.build.static.yaml` after `compose.static.yaml` for the static runtime. Preserve their local image names and build policy; see [deployment](docs/deployment.md#build-container-images-from-source). Native release archives support Linux amd64/arm64, include license notices, and use the host's CA store and optional Chromium; they do not load `.env` automatically.
- Keep concurrency, response sizes, item counts, timeouts and cancellation bounded. A scheduled refresh that renders in Chromium (browser mode, or rendered articles in any mode but FlareSolverr, Auto included) starts only while a `BROWSER_SLOTS` admission is free, as FlareSolverr refreshes do within theirs, and renders one page at a time; a refused feed stays due without failing. An Auto list-page fallback is not admitted, previews and page loads are never refused for Chromium, and only a render that waited out its deadline for a pool slot blames the slot. The scheduler reads the pool's capacity without its lock and never calls `Pool.Stats` under its own. A renderer without `Capacity`, as most test fakes are, keeps four article workers, so a deadline or backlog test of rendered articles also runs with one that has it. Recipe edits must invalidate stale in-flight results and conditional-fetch validators. Pausing and resuming are not recipe edits: `POST /api/feeds/{id}/enabled` (`Store.SetEnabled`) changes only `enabled`, plus `next_run` when resuming a paused feed, never the version, validators, error, failure count or `last_changed`. A card's stale copy then cannot undo an edit saved elsewhere, a running refresh still saves, readers keep receiving 304, and a resumed feed that fails again continues its backoff instead of starting over or alerting again. An editor save keeps the stored setting when the operator left its checkbox alone (`loaded_enabled`), so an open editor cannot undo a card's Pause.
- Preserve destination validation through redirects and exact-IP dialing. Do not bypass it with environment proxies, broad private-network exceptions, or a disabled Chromium sandbox. Local test fixtures use explicit, narrowly scoped network exceptions.
- The shipped example recipes target the demo site in `docs/examples/demo-site`, not third-party publishers: they must keep working offline, and a test imports every example and extracts from that site. Do not add examples that scrape a real site.
- Every response carries the security headers set in `Handler`, including unauthenticated and error responses. The content policy is the second layer behind server-side sanitization for extracted markup, so both layers stay tested; the visual selector frame is the one deliberate override and replaces the policy with a stricter sandboxed one.
- Management mutations require authentication, Origin validation and CSRF protection. Keep the visual page preview isolated and sanitized. Preserve dark mode, field help, and live CSS/XPath highlighting when changing the editor.
- Require configured admin credentials, without imposing a length policy on `ADMIN_PASSWORD`. Preserve full-password matching for long/Unicode values and compatibility with externally supplied bcrypt hashes.
- `PUBLIC_BASE_URL` is the stable public origin without a path prefix. Temporary forwarded browser ports do not become deployment configuration. Check the existing origin tests before changing this behavior.
- Keep SQLite as the default when `DATABASE_URL` is blank or unset. An explicit `postgres://` or `postgresql://` URL selects PostgreSQL; never silently migrate, merge, or replace data when switching. PostgreSQL connections require UTF-8 database/client encoding. Database credentials are trusted configuration, separate from source-fetching `ALLOW_CIDRS`.
- Docker persistence uses precreated host bind directories: `RSS_DATA_DIR` at `/data` and optional `POSTGRES_DATA_DIR` at `/var/lib/postgresql`. Preserve `create_host_path: false`, the app's UID/GID 65532 permissions, and the fixed container `DATA_DIR=/data`. Existing named-volume installations require an explicit migration before changing mounts.
- Run one application process per database for both backends. Schema changes need explicit transactional migrations and a backup/restore compatibility review; do not silently recreate existing data. On PostgreSQL, connecting and a start with nothing to upgrade keep their 10-second bound, while an upgrade runs in a transaction of its own under `postgresUpgradeTimeout`, raises `statement_timeout` with `SET LOCAL` only, keeps the 5-second `lock_timeout` so a second process fails fast, and is cancelled on the server before the process exits when that limit passes or a stop signal arrives. Preserve storage behavior across both backends, including imports, recipe-version checks, scheduling, GUIDs, dates, retention, and reader output.
- An SQLite schema upgrade first saves a copy to `backups/pre-upgrade-schema-<N>-<time>` beside the database, in the backup utility's manifest format, and verifies it with the utility's checks; the native smoke run proves `scripts/backup.py verify` accepts it. The copy is built in a hidden partial directory and renamed only when complete; the next start removes partial directories a killed start left behind. A copy identical to an earlier one reuses it, so a restart loop after a failed migration cannot fill the disk, and a copy that cannot fit is refused before writing. If it fails, the database is left unmigrated and startup stops; only `UPGRADE_BACKUP=false` skips it. Never delete completed copies automatically, and keep the backup utility copying only `rss.db` and its WAL out of `/data`, so these copies never reach its temporary space. Keep the copy's table counts (`backupTables`) in step with the utility's `SCHEMA_TABLES` when a schema adds tables, as schema 6 did not, and add every new schema to its `SCHEMA_VERSIONS`.
- SQLite connection settings (`foreign_keys`, `busy_timeout`) go in the DSN so the driver applies them to every connection; `database/sql` replaces a connection after an interrupted statement, and a setting applied once is silently lost. Opening a supported database first deletes rows whose feed no longer exists, which only finishes deletions an earlier release left incomplete; keep that limited to rows keyed by a deleted feed, and leave every other foreign key violation for the checks to refuse.
- The released schemas are 1 to 6, each frozen in SQLite and PostgreSQL fixtures (`internal/store/testdata/schema_vN.sql` and `postgres_schema_vN.sql`). Schema 2 adds run diagnostics; schema 3 prevents older apps from silently ignoring filters stored in recipe JSON; schema 4 stores fetched article bodies; schema 5 adds library filters and their feed links; schema 6 (v1.3.0) adds `feeds.last_new`, which only a stored merge that inserts a story retention keeps moves and serialization never reads, and its version gate stops older apps from ignoring recipe fields that change output, such as `remove` and `accept_language`. The current schema's fixtures must match the shipped schemas (`TestCurrentSchemaFixturesMatchShippedSchemas`); once released they never change, so later DDL needs a new schema. Retain every released migration and frozen fixture so users can upgrade directly from any released schema without installing intermediate app versions. Test the full transactional chain, existing history preservation and rollback on failure. Keep backup support for every released schema, and derive the tool's user-facing version list from its supported set rather than repeating it; unknown/newer schemas must still be rejected. Downgrades require a backup compatible with the target app version.

## Validation

Use focused tests while editing, then run `make check` for Go or application changes. It includes the deterministic native workflow with temporary credentials, local fixture servers and a disposable database. `make test` and `make check` skip the opt-in Chromium and live-site checks. Their Go commands target `./cmd/... ./internal/...` to avoid walking private runtime and backup directories; use the same package paths for direct Go test commands.

| Change | Additional checks |
| --- | --- |
| Visual editor, embedded UI or Chromium integration | `make browser-test` (sandboxed Chromium and UI fixture tests); add `RSS_UI_DOCS=1` to also capture the documentation images into `artifacts/browser`, then copy them into `docs/screenshots/` (see docs/browser.md) |
| Dockerfiles, Compose, executable paths, deployment wiring or a new environment setting | `make compose-test` (merged configuration) and `make docker-smoke` (both images, including restart persistence). `compose.yaml` passes an explicit variable list, so a new setting needs an entry there, or Docker deployments silently ignore it, plus `.env.example`, the environment table in docs/deployment.md and an assertion in `scripts/compose_test.py` |
| Both of the above | `make check-containers` |
| Backup/restore tooling | `make backup-test` and the opt-in Docker roundtrip below |
| Storage, database configuration or scheduler persistence | `make postgres-test` with a disposable `RSS_TEST_POSTGRES_URL`, plus `make docker-postgres-smoke` |
| Source inventory/release tooling, dependencies or their notices | `make release-test`, which also checks `docs/dependencies.md`, `docs/licenses/` and the notice names in `docs/licensing.md` against the modules `./cmd/server` links (`scripts/check-dependencies.py`); lint workflows with `actionlint` if available |
| Docs only | Check local links, commands, names and consistency with current code/configuration; CI skips `docs/*.md`, so run `make release-test` after editing `docs/dependencies.md` or `docs/licensing.md` |

```sh
# Builds a local static image, then exercises backup/restore using isolated storage.
make docker-static
RSS_BACKUP_DOCKER_TEST=1 RSS_BACKUP_TEST_IMAGE=rss-workshop:static-check \
  python3 scripts/backup_test.py
```

The standalone backup tests require direct Docker CLI access, independently of Make's `DOCKER` variable. If elevation is required, use an explicit command such as `sudo env RSS_BACKUP_DOCKER_TEST=1 RSS_BACKUP_TEST_IMAGE=rss-workshop:static-check python3 scripts/backup_test.py`. The smoke script accepts `DOCKER`, which Make's container targets pass through. Avoid passing the entire environment through sudo.

PostgreSQL tests require a dedicated disposable database via `RSS_TEST_POSTGRES_URL`; never point them at a real library. `make postgres-test` runs PostgreSQL persistence checks, `make postgres-smoke` runs the native workflow against that test database, and `make docker-postgres-smoke` creates its own temporary Compose server and storage. Normal SQLite checks explicitly clear `DATABASE_URL`. Compose tests must supply private fixture paths for `RSS_DATA_DIR` and `POSTGRES_DATA_DIR` rather than inheriting operator settings. Smoke runs likewise point `NOTIFY_URL` and `NOTIFY_TOKEN` at their own local receiver, never an operator's service, and pin the other `NOTIFY_*` settings and `LOG_LEVEL` and `LOG_FORMAT`, whose info lines they check. See [PostgreSQL setup](docs/postgresql.md) for the service contract and PostgreSQL backup commands; the SQLite backup utility must not be used for PostgreSQL.

Browser checks store synthetic screenshots under ignored `artifacts/browser/`. Tests need local listening sockets; a restrictive execution sandbox may require running them with the appropriate permission. Report a skipped or blocked check accurately. Prefer deterministic fixtures to third-party websites; live-site tests are optional and their contents can change. Large feed-count load tests are not part of the required checks. UI tests click anything a script redraws (feed cards, the filter library list and picker, the dashboard status line) with `clickCurrent` or `clickQuery`, which find, check and click it in one evaluation. `chromedp.Click` resolves a node and then reuses its id, so a redraw from the 10-second poll or a library reload makes it fail intermittently. Keep `chromedp.Click` for the page template's own elements, and after signing in again, wait until sign-in has finished before acting.

## Repository and operational hygiene

- Keep `.env`, passwords, cookies, reader bearer tokens, notification URLs and tokens, databases, backups and private source pages out of commits, logs and screenshots. Avoid printing resolved Compose configuration or full container environment inspection because they contain secrets.
- Preserve existing services and data. Identify the current project, container and storage mount before changing deployment settings. Use [operations](docs/operations.md) for verified backups, migration from named volumes, and restore into new storage; never replace a mount with an empty path or use `docker compose down -v` as routine cleanup on a real deployment. Keep custom host storage outside the checkout or excluded from Git and Docker builds. Test scripts clean up their own isolated resources.
- For Gluetun deployments, follow [VPN networking](docs/gluetun.md): publish ports on Gluetun and keep app network sharing intact. A namespace fixture tests Docker wiring, not a real VPN connection or its kill switch; report those verification limits. Keep site-specific overrides in ignored `compose.local.yaml`.
- Keep lasting documentation in the README, contributor guide and relevant topic guide. Update the existing guide when behavior changes; do not add implementation plans, dated progress logs, local-machine readiness reports or temporary test paths to the repository.
- Preserve `LICENSE` and `docs/licenses/`. Dependency or image changes may require updating notices, inventories and matching source archives; follow [licensing](docs/licensing.md) and [releases](docs/releases.md).
- Keep changes focused. Add regression tests for meaningful behavior or failure boundaries, rather than tests that repeat implementation details. Include what changed and what validation actually ran in the handoff.
- CI runs the full matrix for pull requests, manual dispatches and release calls, and only the Go jobs for a push to `main`, because that push retests a tree the pull request already validated. Anything that could pass on a branch and fail after merging must be covered by the Go jobs, or the trigger needs revisiting.
- GitHub and registry publication use the separate manual release process. Stable aliases may advance only after both immutable version manifests and their source checks succeed; preserve prerelease exclusion, downgrade protection and repairable partial promotions. Do not turn local development or testing into a release implicitly.
